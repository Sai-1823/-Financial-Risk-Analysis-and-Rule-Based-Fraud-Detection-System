# Project 21: Contributing Guidelines & Engineering Standards

Welcome to the team repository for **Project 21: Financial Risk Analysis and Rule-Based Fraud Detection System**. These standards ensure our 5-person engineering team collaborates effectively, maintains clean code, and upholds academic integrity.

---

## 🌿 1. Git Workflow & Collaboration

### Branching Strategy
We use standard GitHub Flow. Direct commits to `main` are strictly prohibited.

- Feature branches: `feat/role<N>-<feature-description>`
  - Example: `feat/role3-dynamic-weights`
  - Example: `feat/role2-patch-review-endpoint`
- Bug fixes: `fix/<issue-description>`
- Testing/QA: `test/<test-suite-description>`

### Pull Requests (PRs)
1. Every PR must have at least **1 peer review** approval from another team member before merging.
2. PR description must reference which of the 5 roles is affected and include steps to verify.
3. CI/pytest must pass 100% on the branch.
4. Merge using **Squash and Merge** with concise commit titles.

### Commit Message Standard
Follow Conventional Commits:
- `feat(rules): add dynamic threshold adjustment to engine`
- `fix(api): handle missing region in transactions filter`
- `test(rules): add edge test case for midnight boundary`
- `docs(readme): clarify SQLite vs MySQL connection flags`

## 🤖 2. Responsible AI Usage Policy

Generative AI (e.g., Google AI Studio, Gemini, LLMs) may be utilized as a pair-programming accelerator subject to the following strict guardrails:

1. **Human Understanding Mandate:** No student may commit code generated by AI that they cannot thoroughly explain line-by-line during our team demo and grading defense.
2. **Deterministic Security Rules:** All mathematical weights and rule thresholds must be explicitly validated against project guidelines. Never permit an AI tool to silently alter weights or remove validation logic.
3. **Synthetic Data Integrity:** Never feed real bank credentials, personally identifiable information (PII), or confidential data into AI prompts.
4. **Attribution:** When AI is used to bootstrap tests or boilerplate, note the prompt intent in the PR description for academic transparency.

## 📐 3. Coding Standards & Conventions

### Python Backend (Roles 1, 2, 3, 5)
- **Style:** Strictly adhere to PEP 8 standards with 4-space indentation.
- **Type Annotations:** All functions must have explicit type hints (`typing.Optional`, `typing.List`, `typing.Dict`, `typing.Tuple`).
- **Docstrings:** Use Google-style or NumPy-style docstrings documenting arguments, return values, and mathematical rationales.
- **Error Handling:** Always return standard HTTP exceptions with descriptive JSON messages (`raise HTTPException(status_code=400, detail=...)`).
- **ORM Integrity:** Never use raw concatenated SQL strings. Always use SQLAlchemy parameter binding or ORM queries to prevent SQL injection.

### Frontend Dashboard (Role 4)
- **State Management:** Clean separation of presentation and API data fetching.
- **Graceful Fallback:** If the backend API is unreachable or restarting, fallback smoothly to the interactive simulation state without unhandled console errors.
- **Accessibility:** High-contrast color indicators, keyboard navigable tables, and accessible ARIA labels.

---

## 🧪 4. Testing Requirements

- Any new rule or heuristic modification in `app/rules/engine.py` requires corresponding test cases in `tests/test_rules.py` covering:
  1. Positive trigger (condition met)
  2. Boundary condition (threshold - epsilon, threshold + epsilon)
  3. Negative case (benign baseline)
- Any new API endpoint in `app/api/` requires unit/integration coverage in `tests/test_api.py`.
- Run before submitting any PR:
  ```bash
  pytest -v --maxfail=1
  ```
